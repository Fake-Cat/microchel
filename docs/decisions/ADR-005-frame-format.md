# ADR-005: Формат кадров — PNG с длительностью в имени файла

**Статус:** принят (2026-10-08)

## Контекст

PHASE 2 требует выбор формата хранения анимаций. Концепция запрещает массовую конвертацию изображений до установления исходных форматов.

## Что установлено в VPet

- Кадры — обычные PNG с alpha.
- Имена вида `_NNN_DDD.png`: `NNN` — порядковый номер кадра (000, 001, …), `DDD` — длительность кадра в миллисекундах (250, 125, 375, …).
- Иерархия: `mod/<mod_id>/pet/<персонаж>/<Анимация>/<Состояние>/<Линия>/<кадры>`, например `vup/Default/Nomal/1/_000_250.png`.
- Длительность per-frame прямо в имени — отдельный конфиг FPS не нужен.

## Рассмотренные альтернативы

- **Sprite sheet + JSON (FPS, loop)**: компактнее, но конвертация и свои инструменты.
- **GIF/APNG/WebM**: проблемы с прозрачностью/качеством/памятью на RPi.
- **Нативный формат VPet (`_NNN_DDD.png`)**: совместимость, простота парсинга, гибкие тайминги.

## Решение

Анимационный движок читает каталоги кадров в нативном формате VPet: `_{номер:03d}_{длительность_мс}.png`, сортировка по номеру, длительность — из имени. Формат документируется как основной; при необходимости в него конвертируются другие исходники (конвертер — scripts/, позже).

## Причины

- Совместимость с ресурсами VPet (при их использовании) без конвертации.
- Per-frame тайминги без внешнего конфига; простой парсинг; обычные PNG доступны везде.

## Последствия

- Имена файлов — часть API формата: ломаешь имена — ломаешь движок.
- Много мелких PNG = много файлов; нужен кэш и ленивая загрузка (ограничение памяти RPi).

## Ограничения

- Не подтверждено чтением кода GraphCore/PNGAnimation VPet (изучено по структуре репозитория). Проверить при глубоком исследовании PHASE 2.
