# ADR-006: Резолюция прокси для LLM-запросов

**Статус:** принят (2026-10-11)

## Контекст

Gemini-провайдер работает через сеть; в целевом окружении (РФ) доступ к `generativelanguage.googleapis.com` возможен только через прокси. Прокси не должен хардкодиться в коде или конфиге репозитория (разные машины/сети).

## Рассмотренные альтернативы

- **Только переменная окружения `https_proxy`:** стандартно, но неудобно переключать per-run (напр., тест «напрямую vs прокси»).
- **Только конфиг `agent.toml`:** удобно для постоянной машины, но требует правки файла для разовых запусков.
- **Приоритет CLI > конфиг > окружение > прямое соединение:** гибко и предсказуемо.

## Решение

`resolve_proxy_url(cli_proxy, config_proxy, environ)`: первый непустой источник по приоритету `--proxy` (CLI) → `proxy_url` (config) → `https_proxy` / `HTTPS_PROXY` / `http_proxy` / `HTTP_PROXY` (окружение, включая `.env`) → прямое подключение (пустая строка). Пустая строка в CLI/конфиге означает «перейти к следующему источнику», а не «отключить прокси».

## Причины

- Разовые прогоны (CI, диагностика) — через `--proxy`, постоянная машина (RPi) — через конфиг; окружение — общий механизм для обоих.
- Явный порядок устраняет «почему прокси берётся откуда-то ещё».

## Последствия

- Документировано в `config/agent.toml`; `HttpClient` получает уже разрешённый URL (`ProxyHandler` при непустом, иначе прямые хендлеры).
- Юнит-тесты приоритета — `tests/unit/test_agent_config.py`.
